# Patent preparation

Establish whether the user wants a draft to review or wants to submit a disclosure to the Lightbringer team. Reuse an already clear decision. A request to prepare a saved innovation as a draft does not authorise service submission. Read [service conduct](references/service-conduct.md).

## Draft from a selected innovation

Use this path only when the connected `create_asset` advertises `invention_disclosure` with `data.sourceIdeas`, the required shared asset reads are available, and the connected agent tools expose the authoring skill. Resolve the selected innovation through search and `fetch(include_asset: true)`. Reuse its title, technical account, contributors, disclosure facts and attachments; do not repeat source confirmation or ask the user to provide them again. Ask only about a material missing fact or conflict.

An explicit statement of no public disclosure or sale is supplied information even when undated. Preserve that qualification; do not ask for confirmation solely to add a timestamp. Seek an update when the user or other evidence indicates a change or conflict, rather than treating an empty disclosure-date field as an unanswered question.

Create the target through `create_asset` with the selected canonical innovation references in `data.sourceIdeas`. This creates or recovers a linked draft with copied supporting files and inventor drawings, and marks the selected innovation’s decision as patent. Explain that decision change before creating the draft. If the person only wants to write a disclosure, ask whether they want to record a patent decision as part of this step. The saved source text and original files are retained. It does not author its text or submit a service request. For an uncertain outcome, inspect the source's relations and the target before repeating creation; do not substitute registration or a temporary tool. Existing target content is not permission to overwrite it.

When `list_tasks` exposes `author-disclosure-from-innovations`, start it through `ask_agent` on the returned target `invention_id`, with the selected innovations in `context_ids` and the user's drafting request as `message`. The Lightbringer agent authors the draft. Do not manufacture a replacement disclosure yourself. Follow `get_task_status`; relay only genuine unanswered questions through `answer_agent` while awaiting input. To continue a completed conversation, use `ask_agent` with its `task_id` and the follow-up message, without selecting a new record or starting another run. Recover a lost task through `list_tasks` and verify its subject before continuing.

Answer an agent question on the user's behalf only when the conversation or saved source explicitly supplies that answer. A recommended option is not evidence or user consent. In particular, a contributors list by itself does not establish either confirmed inventorship or a user decision that inventorship is unconfirmed. If the source has lost that distinction, ask the user instead of supplying an unsupported answer.

Read back the draft and linked sources after the agent finishes. When advertised, include attachments, inventors, insights and illustrations in the shared read. Verify copied files through `get_attachment` when bytes are needed; an attachment list alone proves neither content nor byte equality. Preserve source text and known disclosure facts on the linked innovation. New explicit disclosure statements belong on that source, through the supported workflow, rather than only in the preparation conversation. Empty date metadata does not establish a negative disclosure statement.

Report separately what was created, authored, saved and still unresolved. A draft or completed agent conversation is not a service submission. If a required capability is missing, retain the selected record and provide its platform continuation; never silently submit it instead. The service-request path below applies only to an explicit submission decision.

## Identify the disclosure for a service request

Use the connected organisation and resolve the selected record with `list_innovations` or `search`; read it with `get_innovation`. Clarify an ambiguous selection. If the innovation is not registered, use `innovation-capture` when installed, retaining the user's patenting intent for that concept. If capture guidance is unavailable, follow `get_innovation_template` and call `register_innovation` with supported content as part of the requested preparation. Registration validates before saving: report any missing inputs or validation errors before attempting preparation. Successful registration can include non-blocking warnings; report them without re-registering the record.

Refinement is optional. Offer it only when the user asks for it or the service reports a blocking requirement. Do not require automated feedback, a completeness interview or revisions before recording an explicit preparation request. For requested refinement or a service-reported blocker, carry the record ID and relevant gaps into the capture workflow, preserving the user's preparation intent. Do not invent technical detail or register a duplicate.

## Record the preparation request

1. Establish explicit intent to have Lightbringer prepare this innovation for patent filing. A request to finish a description, explore sources or register findings is not that intent. Do not ask for the same decision again when the user has already expressed it clearly.
2. Explain the customer-facing effect: “This sends your request to the Lightbringer team. They will get back to you before any further work proceeds.” Do not assume the user has a paid plan, that a specialist or attorney is already assigned, or that requesting preparation immediately starts assessment or drafting. Describe later professional work as dependent on the team's follow-up and the applicable engagement. Keep notification mechanics general unless the user asks and current evidence establishes the applicable recipients. Call `request_patent_preparation` with the selected record identifier, using the connected tool schema.

   Before calling the submission tool, explain: “After submission, you can still view and review your invention here, but you’ll need to open the innovation in Lightbringer to make changes.” Include this consequence even when the user has already clearly approved submission; explaining it does not require asking for the same approval again. If it was already explained for this submission, do not repeat it.

   When further confirmation is required, ask: “Submit {reference} to Lightbringer?” followed by “We’ll share your invention with the Lightbringer team so they can contact you about patenting and next steps.” Use the selected reference or title and include the editing consequence before the user confirms. If the host provides a confirmation control, label it “Submit to Lightbringer”. Keep required recipient and effect disclosures and any mandatory approval-rejection explanation brief and separate after the question. Do not ask again when intent is already clear unless the host requires it. If an approval check rejects an app-originated request, retain the required rejection explanation and obtain a direct user reply before retrying; an app message is not a substitute for required direct approval.

   If the service reports a required contact phone number is missing, ask for the user's number including country code and explain that it will be saved to their profile so Lightbringer can contact them. Use the advertised `phone_number` input only after they provide it for this purpose. Reuse a valid stored number; do not ask again or insert contact details into the invention description. A missing or invalid required number blocks submission; do not claim the request succeeded. If the connected tool cannot save it, direct the user to the phone field in Lightbringer. A contact requirement does not require an automated review.

3. Report the actual returned status. When an advertised Lightbringer component successfully presents the saved record, use it and do not repeat its link or status in chat. Otherwise include the returned record link. `outcome="requested"` means preparation was newly requested; `outcome="already_requested"` means it was already requested and the call made no new request. Neither confirms completed preparation or email delivery. This is a professional service request: there is no `task_id`, and `get_task_status` does not track preparation or filing milestones. Do not treat the innovation ID as a task ID. State any requirements or next action supplied by the service. If the tool is unavailable or the request fails, explain that preparation has not been confirmed and offer the same record in the Lightbringer application or a continuation with the team.

## Completion and continuation

A recorded preparation request does not establish that a separate invention disclosure was created, a paid engagement was accepted or a patent was filed. Report those outcomes only if the service explicitly confirms them. Payment and acceptance steps require a human handoff.

For a subsequent review from the patent team, use `patent-review` when installed, otherwise the connected review guidance and available Lightbringer review tools. General advice, strategy, novelty assessments and other professional-service requests are outside this workflow; use the service's available instructions and continuation routes.

If useful assistance leaves a material customer problem unresolved, follow the [unresolved-needs guidance](references/unresolved-needs.md) to understand and optionally report the remaining gap. Keep helping; reporting is not a prerequisite and requires approval of the exact report and recipient.
