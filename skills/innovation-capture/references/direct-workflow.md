# Direct innovation workflow

Read this for direct record work or when the advertised capture journey is unavailable. Guided capture follows the main skill and capture-handoff reference instead.

## Scope and context

Use the connected organisation and the user's existing technical context. Establish which sources are in scope and whether the user wants analysis, registration or an update. Carry out requested saves without asking for the same approval again. Clarify an ambiguous record, source scope or requested change before acting. An exploration-only request does not authorise saving findings.

Use the organisation's IP strategy when available. When advertised, prefer `search` with its Strategy category and `fetch` with advertised `include_asset: true` for structured Strategy state; if the replacement read contract is unavailable, use the deprecated `list_strategies` and `get_strategy` compatibility tools to locate and read relevant published Strategy records; multiple strategies may apply to the source scope. Treat drafts and records with unknown publication status as proposals, not adopted direction. Publication makes a strategy shared context but does not establish that every recommendation has been approved.

Organisations may also record strategy decisions in reports. Use `search` and `fetch` to find relevant reports when no applicable published Strategy is accessible or a relevant decision is not covered. A result's title or `report` category does not establish its kind, publication status or adoption; resolve Strategy identity and status through structured fetch state, using deprecated `get_strategy` only when that read contract is unavailable. Distinguish adopted decisions from proposals in reports, uploaded documents and meeting notes, and state conflicts or uncertain adoption. Record fit and uncertainty without discarding innovations for low alignment or uncertain patentability.

If no applicable strategy is found in the accessible sources, recommend creating one in Lightbringer to connect innovation capture to business objectives and protection priorities. Explain any lookup or access limits rather than assert that no strategy exists. Where a relevant draft already exists, offer to develop that record instead of creating a duplicate. If the user takes up the recommendation, use `ip-strategy` when installed or the connected Strategy capture guidance. Otherwise continue authorised innovation capture with explicit working assumptions; the recommendation does not itself authorise creating or publishing a Strategy.

## Gather supported context

Adapt to the request; a conversation can lead to source exploration and back again.

Use the person’s own words for their idea. Call the saved note an innovation and the document prepared for review an invention disclosure. After a confirmed save, use the title or their own description and give them the link to reopen it. A simple save can end there.

For a rough idea, start with the next useful question in ordinary language, usually about how the proposed solution works. Build on the answer instead of presenting a multi-topic intake checklist. Reuse facts already supplied, including who came up with the idea; ask for clarification only where the meaning or attribution is unclear. Bring up other relevant gaps naturally as the conversation develops. Unknown details can stay open and should not turn a simple save into a complete disclosure interview.

- **Conversation or inventor interview:** prefer the available guided-capture journey above. In the direct-authoring compatibility path, retrieve `get_innovation_template` and follow its current interactive guidance and readiness criteria. Reuse supplied context. For a targeted enrichment, read the existing record and clarify only what the requested change needs; do not restart capture.
- **Source exploration or patent mining:** read [source exploration](source-exploration.md). Investigate the authorised material, trace supporting evidence and retain identified innovations even when incomplete. Do not require a broad mining exercise for a single idea.

## Choose the saved record

Check the connected schemas before starting an interview. For a requested save, use `create_asset` when it advertises `type: innovation`. Include the title, supported Markdown, contributors and known public-disclosure facts. Do not force a full invention-disclosure questionnaire or change the record type to satisfy a missing capability. Preserve unknowns; a missing disclosure date is not evidence of no public disclosure. When the user wants an invention disclosure instead, use the advertised `invention_disclosure` variant and its current capture guide. When that disclosure is based on an already saved innovation, follow the selected-innovation draft flow in `patent-preparation`: author from the source using the template, then save the completed definition with its source references in the same registration. The `invention_disclosure` variant and the deprecated `register_innovation` both save a disclosure; neither is a substitute for lightweight innovation capture.

## Preserve supported facts

For a lightweight innovation, put the technical description in a “Source description” section as attributed Markdown blockquotes copied from the original user messages or authorised source documents. Select the relevant technical passages without rewriting them; keep each passage's conditions and qualifications intact. Use the actual source, not your own summary or skill-call arguments. Organise inventor statements, status and open questions separately. Do not add a second paraphrase as a problem, mechanism or benefit section. When combining sources, keep their excerpts and attribution separate. An explicit request to rewrite permits editing the wording, not adding facts; label the edited text as a draft rather than a quotation. For a targeted update, preserve unrelated content and record the supplied amendment without silently changing an earlier quotation.

Before each create or update call, compare the actual save content with those source passages, clause by clause. Keep stated drawbacks and intended benefits separate: a benefit does not establish the opposite property in an existing approach. Remove unsupported comparisons and claims before writing. After saving, compare the persisted content returned by the tool with the source and requested changes. If the response contains only a receipt or omits the changed content, fetch the record through the advertised asset read. Correct any introduced discrepancy within the authorised scope before confirming completion; a success flag or record link alone is not a factual check.

When condensing technical explanations, preserve quantities, negations and uncertainty, and keep each condition, timing constraint and exception attached to the operation it qualifies. A condition on updating a calculation does not establish when the calculation starts or runs. If smoother wording would add an assumption, retain the source wording or leave the unresolved distinction explicit.

Preserve the user's explicit inventor statement in the innovation's Markdown as well as the names in `contributors`: for example, “The user identifies A and B as the inventors.” The generic contributors list alone does not retain that statement for a later preparation conversation. Conversely, names supplied only as contributors are not confirmed inventors. An account or host profile name alone does not establish the inventor's name: retain “The user identifies themself as the inventor” until the person is explicitly identified in the invention context. Retain any uncertainty or qualification the user gave; do not make a legal determination. Likewise, save an explicit statement of no public disclosure or sale in the innovation's text, rather than only in the conversation or an empty date field. Read back these facts after saving.

## Read and update existing records

For shared asset reads, use `fetch(include_asset: true)` when advertised. Keep its canonical reference and revision. Tools that take an `invention_id`, such as `start_innovation_feedback`, `list_tasks` and `request_patent_preparation`, receive that reference without its `document:` prefix; every version of those tools accepts that form. Prefer the matching `update_asset` variant for authorised changes, preserving omitted fields and content. A stale revision requires a fresh read and reconciliation. A missing required read, denied permission or uncertain write does not justify switching to a legacy writer or creating a duplicate. Confidential records may be unavailable to assistants; offer their platform link instead of reconstructing protected content from chat memory.

An innovation's `contributors` is the complete list of display names. When an update changes it, send every name from the fetched state that should stay, because omitted names are removed; keep a name unless the user asks to remove it. Listing a contributor is credit only: it grants no access and invites nobody. Use the invitation guidance below when someone needs access.

The sequence below uses the shared asset tools. It names the deprecated `list_innovations`, `get_innovation`, `register_innovation` and `update_innovation` only as fallbacks for a connection that does not advertise the corresponding search category, asset read or `invention_disclosure` variant. It does not override an advertised innovation workflow. For requested drafting from a saved innovation, continue with `patent-preparation`; saving an innovation alone does not start that work.

## Match, register or enrich

1. Search for the same concept with `search`; its `innovation` category covers saved innovations and invention disclosures not yet submitted for drafting. Also check the advertised application category when a submitted disclosure may already exist. Read likely matches with `fetch` and `include_asset: true`. Use `list_innovations` and `get_innovation` only when that category or read is not advertised. Compare the idea and mechanism, not just titles. Reuse an existing record, including a previously rejected one when factual enrichment is relevant and permitted. Preserve decisions and sources; never create a duplicate to bypass a restriction.
2. For a disclosure without an existing source innovation, retrieve `get_innovation_template` and read [authoring guidance](lightbringer-authoring.md). Draft from supported context and, only when registration is authorised, save it with `create_asset`, sending `type: invention_disclosure` and the completed definition as `asset.data`. Use `register_innovation` only when that variant is not advertised. If neither is advertised, keep the disclosure in the conversation as pending registration and offer the Lightbringer link; do not save it as a lightweight innovation instead. Registration validates before creating anything. Validation errors mean nothing was registered: correct the reported fields using supported facts before retrying. On success, report the saved record and any non-blocking warnings; do not register again because of warnings. If the schema cannot represent the available information honestly, retain the innovation in the summary as pending registration and identify the missing inputs.
3. For an existing disclosure, read it with `fetch` and `include_asset: true`, then send `update_asset` with its reference, the current `revision` and complete replacement text in `changes.sections` for the sections being changed. Omitted sections stay unchanged. A stale revision fails without writing; fetch again and reconcile before retrying. When that variant is not advertised, use `update_innovation`, reading the record first with `fetch` or, where that read is not advertised, `get_innovation`; inspect each section's `applied`/`error` result and report any unsaved changes. If neither write is advertised, keep the proposed changes in the conversation and offer the record's Lightbringer link. Preserve earlier supported content. Follow the tool's section names; they differ from the registration payload fields. Do not re-register an existing record to validate an update. Report any `warnings` and `orphaned_discussion_ids` that `update_asset` returns. Inspect the optional `dropped`, `detached_threads` and `marks_incomplete` receipts that both tools return: a successful write does not establish that all formatting or comment anchors survived. Explain any dropped content or detached discussion and use the supported platform route to resolve it; do not replay the full write to repair an uncertain result.
4. If refinement is requested, use `start_innovation_feedback` with the record ID without its `document:` prefix. This is automated analysis of the description, not a novelty search or professional assessment. The response contains one `task_id`, `status`, `progress`, and available per-analysis `results`. While `queued` or `running`, poll `get_task_status` with that same `task_id`; it returns the same contract. Stop at `succeeded`, `partially_succeeded`, or `failed`, and report failures alongside available findings. Findings have readable `title` and `description` fields, with optional categories and supporting details. A `findings_error` means the findings could not be returned; report this limitation rather than claiming there were no findings or continuing to poll a terminal task. Ending the wait does not cancel analysis. Apply authorised improvements supported by the evidence; leave remaining gaps explicit.

Tasks and findings expire 30 days after creation; reading does not consume them or extend retention. Use `list_tasks`, optionally filtered by `invention_id` (the record ID without its `document:` prefix), to recover a lost task ID in the connected organisation. Follow `next_cursor` even if access filtering returns an empty page; listing reports recorded status without polling. `delete_task` permanently removes the user’s task and findings when requested, in any execution state, with write consent. Deletion does not cancel the analysis, delete the innovation or withdraw a service request.

For an authorised inventor-name correction, fetch with `include_inventors: true` when available and retain every existing inventor ID in the complete desired list sent through `update_asset`. Preserve other inventors; omit an ID only for a new person. Refused assignment locks are not bypassed by replacing the inventor. Read back the saved result.

## Illustrations and source files

For a requested illustration upload or vault source, read [files and illustrations](files.md). Add drawings to the selected draft innovation through the available upload tools, with optional illustration readback only when advertised. A file supplied as evidence is not automatically authorised for upload. Vault storage is a separate destination and does not attach a file to the innovation. Direct requests to add a drawing do not require repeating capture or automated feedback.

## Present automated feedback

After requested feedback, read the available results across the whole run before selecting what to show. While analyses are still running, describe any selection as provisional and retain the unfinished/failed analysis status; do not treat a progress snapshot as a completed review or restart it to obtain the missing results.

Present **up to five priority findings in total**, not five per analysis. Select fewer when fewer matter; do not fill a quota. Prioritise uncertainty about the core technical mechanism and evidence supporting it, then missing information needed to understand or implement the described invention. Merge overlapping findings across analyses into one focused item, retaining their source support and material qualifications. Keep each item to a short title and one main action in a brief sentence, with supporting explanation available on expansion or request. Preserve uncertainty, conditions and the distinction between proposed and demonstrated features. Do not turn a detailed finding into several superficially separate priorities. Omit problem restatements or already-described benefits from the shortlist unless they identify a specific unresolved gap.

Separate optional new embodiments or extensions from gaps in the invention as described. Show up to three optional ideas, secondary and collapsed where supported, rather than implying they are required improvements. Do not invent alternatives solely to populate this section.

When the advertised presentation tool supports a source-linked review summary, supply the merged shortlist through its current schema, citing the actual supporting findings from the existing task. Follow its source-index and length limits; never invent references, cite discarded/unavailable findings or imply the summary is verbatim analysis output. If that schema is unavailable, provide the same concise synthesis in text or the supported presentation format without sending unadvertised fields. When an MCP app delivers the findings, do not repeat them or the saved-record link in chat.

Keep the complete returned findings accessible from the **same run**, through expansion when supported or by reading the existing task on request; explain any availability/expiry limits. A display limit must not discard findings or require a new paid analysis to reveal them. Work through selected findings as described below. Offer re-review after meaningful changes or on explicit request, reusing the current record and distinguishing unresolved, resolved and newly found issues; do not rerun automatically or promise an exhaustive or patent-ready result.

## Work through selected findings

Use the user's selected findings and optional ideas as the scope for a short question queue. Ask one focused question at a time, reusing answers already supplied. After each response, show a compact progress count such as **Answered 2 of 4 questions**, followed by the next question. Count actual questions in the agreed queue, not every raw analysis finding. If a necessary follow-up expands the queue, update the total explicitly. A clear “unknown” or “TBD” is an answer to record; it does not resolve the technical gap. Keep skipped questions and unresolved gaps distinct from answered questions, and never describe the invention as fixed merely because the interview is complete.

Keep proposed disclosure edits separate from the saved record while discussing them. When the queue is complete, or the user chooses to finish early, show the final progress count and a concise preview of the proposed updates, including remaining unknowns. Ask whether the user wants to save those updates to the existing invention; completing the questions or selecting findings does not authorise saving. If the user already approved that exact set of edits, proceed within that approval instead of asking again. Keep unsaved answers available in the conversation if saving is declined, deferred or unavailable.

After approval, read the latest saved disclosure, preserve unrelated supported content, and apply only the approved updates through the available edit contract. Inspect the write outcome and read back the affected content before confirming what was saved. Keep any failed or unsaved changes explicit. Answered, resolved and saved are separate states; offer a new review only when useful and explicitly requested.

## Completion

Return a brief summary of actual outcomes, evidence used and remaining questions. For automated feedback, use the focused presentation above. When a relevant Lightbringer MCP app is advertised and successfully delivers the saved record or review, do not repeat its link, findings or summary in chat; include only useful context outside the app. If the app is unavailable, denied, fails or the user requests text, include the saved record ID/link and a concise text response. For exploration, state source coverage and distinguish identified innovations, unresolved problems and sources with no findings. Clearly separate analysis-only findings and failed or pending saves from registered records. A file is optional; local filesystem access is not required. Drawing descriptions do not establish that files were uploaded.

Registration or enrichment completes this workflow. After a confirmed save, co-inventors or contributors may need to validate the record: follow [inviting collaborators](inviting-collaborators.md) to offer once to invite them, or when the user asks to invite someone. For an explicit request to have Lightbringer prepare a selected innovation for patent filing, continue with `patent-preparation` when installed, retaining the user's stated intent. If that skill is unavailable, follow the connected `request_patent_preparation` instructions for that separate request. For review comments or decisions, use `patent-review` when installed, otherwise the connected review guidance and available Lightbringer review tools.

If useful assistance leaves a material customer problem unresolved, follow the [unresolved-needs guidance](unresolved-needs.md) to understand and optionally report the remaining gap. Keep helping; reporting is not a prerequisite and requires approval of the exact report and recipient.
